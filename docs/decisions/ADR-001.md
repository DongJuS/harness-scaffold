# ADR-001: Adopt 200-line file limit and INDEX.md navigation convention

## Status

accepted

## Supersedes

none

## Superseded By

active

## Depends On

none

## Date

2026-04-21

## Background

HarnessScaffold is a self-documenting hierarchical repository scaffold designed
to be maintained by both human developers and AI agents. The project needed a
structural convention to keep files navigable, prevent unbounded growth, and
ensure AI agents with limited context windows can work effectively. This was
the foundational decision establishing the two core conventions.

## Context

This project is a self-documenting repository scaffold designed to be maintained
by both human developers and AI agents. AI agents have limited context windows
and work best with small, focused files. Humans navigating unfamiliar codebases
waste time searching for the right file. Without structural constraints, files
grow unbounded, directories become opaque, and both humans and AI lose track
of where things live.

## Options

### Option A: No file size limit, flat directory structure

- **Pros:** No overhead, maximum flexibility, no tooling required
- **Cons:** Files grow to thousands of lines, agents can't fit them in context,
  new developers can't find anything, no enforced organization

### Option B: Modular convention with per-directory README.md

- **Pros:** Standard practice, GitHub renders README.md automatically
- **Cons:** README.md is overloaded (project docs vs. navigation), no
  enforced size limit, convention easily ignored without tooling

### Option C: 200-line file limit with mandatory INDEX.md per directory

- **Pros:** Forces single-responsibility files, INDEX.md is a dedicated
  navigation tool (not overloaded), small files fit in AI context windows,
  tooling can enforce the convention automatically via validate.sh
- **Cons:** Requires discipline and tooling, splitting files adds overhead,
  some files naturally want to be longer

## Decision

Option C: Enforce a strict 200-line limit on every file and require an
INDEX.md in every directory that maps purposes to file paths.

## Reasoning

The 200-line limit is strict enough to force meaningful decomposition but
generous enough to hold a complete, focused unit of work. INDEX.md serves
as a machine-readable and human-readable map that answers "where do I put
this?" and "where do I find that?" without reading every file. The combination
makes the repository self-documenting: any agent or developer can navigate
from REGISTRY.md to the right directory to the right file by following
INDEX.md files at each level. The convention is enforceable via validate.sh,
which catches violations before they're committed.

## Consequences

### Enables

- AI agents can read any file in a single context window load
- New developers find files by following INDEX.md navigation chains
- Automated validation catches structural drift before commit
- Files stay focused on a single responsibility

### Costs

- Developers must split files when they approach 200 lines
- Every new directory requires an INDEX.md (automated by create-index.sh)
- Some conceptually unified code may be split across multiple files
